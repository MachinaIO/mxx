# Exact-Signal `Large` Residual Debugging History

This document prevents repeated or overlapping fixes while debugging operational-noise
simulation. Read it before changing exact-signal cancellation, relation selection, polynomial
expansion, or `Switch` normalization. Update the table after every materially new attempt.

## Intuitive terms

- **`Large`** means that a matrix is intentionally not assigned a small finite coefficient bound.
  Public keys, uniform residues, and unhashed public matrices can be `Large`. A final noise
  residual containing `Large` cannot be accepted by the threshold check.
- **Exact signal** is algebraic data that may be `Large` but is supposed to cancel exactly. It is
  not noise and must never be made artificially bounded merely to pass Tall.
- **Selected expression** is the one expression chosen from each e-class by extraction. An
  e-class may contain several equal physical representations, but structural normalization must
  operate on one deterministic selected representation.
- **Physical Add** is an actual `MatrixAdd` e-node stored in an e-class. Two physical Adds in the
  same e-class are alternatives, not operands that must be combined or made to agree.
- **Redex** is one selected location where an exact rewrite or normalization can still apply.
- **Ordered monomial spine** is a product represented by its factor sequence plus one sign.
  Matrix multiplication is not commutative, so factor order is preserved.
- **Polynomial consolidation** means interpreting selected `Add`, `Negate`, and `Multiply` through
  one signed ordered-monomial evaluator, instead of maintaining several independent notions of
  additive normal form.
- **Switch hoisting** removes selector-independent work from every case. For example, a common
  term is moved out of `Switch(selector, common + x_i, ...)`, and a common ordered product prefix
  or suffix is moved around the residual Switch.

## Evidence labels

- **Confirmed**: supported by committed source, a retained test, or captured Tall output.
- **Reported run**: observed in an earlier Tall run in this debugging thread; useful historical
  evidence, but rerun before using the number as a current performance baseline.
- **Inference**: a diagnosis consistent with the selected expression but not yet proved by a Tall
  run after the proposed correction.
- **Superseded**: once explained a real supporting defect, but is not the current final-`Large`
  root cause.

## Mandatory pre-change checklist

Before any new exact-signal cancellation or Switch-normalization change:

1. Search this table for the same generalized problem and attempted method. State why the existing
   method is insufficient before adding another one.
2. Capture authoritative current evidence: selected first-`Large` witness, remaining relation and
   structural redex counts, relevant selected operators, and a reproducible command or test.
3. Mark diagnoses as confirmed, inference, or superseded. Do not convert a plausible path into a
   claimed root cause.
4. Reuse the existing selected expression, `ReplacementPlan`, relation provenance, and bound
   resolver. Do not add a second cache, database, normalizer, or fixture-specific identity.
5. Count newly introduced concepts or data structures cumulatively. On every third addition, pause
   and audit whether all three are necessary, whether an existing representation can absorb them,
   and whether the change can delete at least one competing authority. Record that audit here.
6. Keep exact signal and bounded noise separate. Never make `HashPlain`, a public key, or an
   arbitrary artifact bounded merely to make Tall pass.
7. For a narrow implementation correction, run focused tests and then the authorized Tall test
   before requesting Sol review. Request Sol first for a medium or larger semantic design change,
   or when the implementation has become materially more complex.
8. Record elapsed time, redex/union counts, terminal witness, and code-size balance after the run.
   Compare release with release and identical parameters with identical parameters.
9. Update this table immediately after each materially new attempt, including unsuccessful and
   reverted attempts. Do not wait until the final solution.
